# T-002 — Criar e consultar um anúncio aprovado

## Critério para revisão

Dado um anúncio válido e uma resposta HTTP 200 com status approved da moderação, quando o cliente faz POST /ads, então a API persiste o anúncio no Postgres e devolve 201 com ID, dados, status approved e Location apontando para /ads/{id}. Após reiniciar a aplicação com a mesma base, GET nesse endereço devolve 200 com os mesmos dados.

## Entrada de exemplo

```json
{
  "title": "Bicicleta urbana",
  "description": "Bicicleta usada em bom estado.",
  "price": 800.25,
  "category": "esportes",
  "images": ["https://example.org/bicicleta.jpg"]
}
```

O resultado acrescenta id, createdAt, status e rejectionReason nulo. O POST, o GET e a chamada à moderação usam preço em reais. Neste exemplo, `price: 800.25` representa R$ 800,25. A T-002 usa `numeric` no banco. A mudança para centavos inteiros registrará internamente `80025`, conforme a decisão em [DECISIONS.md](../../DECISIONS.md).

## Execução proposta

1. Criar teste pela API HTTP com Postgres isolado e servidor de moderação controlado.
2. Confirmar que a falta da rota causa 404 onde o teste espera 201.
3. Implementar controller, serviço, persistência e cliente HTTP Axios com URL configurável.
4. Verificar que o cliente envia somente title, description, price e category ao endpoint documentado POST /v1/moderation/check.
5. Reabrir a aplicação antes do GET para comprovar persistência.
6. Documentar o contrato implementado e abrir um PR para revisão humana.

Reprovação, validações completas, falhas da dependência e listagem serão cobertas nas fatias seguintes. A integração usa o contrato fornecido e preserva o código do mock.
